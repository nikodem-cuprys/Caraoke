# ROLE

You are a senior full-stack engineer, audio/DSP engineer, machine-learning engineer, UX designer, and technical architect.

Your task is to DESIGN, IMPLEMENT, TEST, and DOCUMENT a production-quality web application that helps users learn how to sing songs.

The main user experience must be extremely simple:

1. User pastes a YouTube link.
2. The application identifies the song/video.
3. The application obtains or asks for an authorized audio source when required.
4. The application processes the song.
5. After processing, the user receives an interactive karaoke-learning experience containing:

   * synchronized lyrics,
   * word highlighting,
   * instrumental/backing track where legally available,
   * isolated/reference vocals where permitted,
   * detected melody/pitch,
   * visual pitch guidance,
   * playback controls designed for practicing difficult sections.

Do NOT produce only an architecture document, mockup, pseudocode, or proof of concept.

If you have access to a development environment, actually create the project, install dependencies, run it, test it, fix errors, and leave a working application.

---

# PRODUCT CONCEPT

Build a web application tentatively called:

**SingLearn**

The application should help someone learn both:

1. the WORDS of a song,
2. the TONES / MELODY of a song.

The goal is not merely to display lyrics.

The application should act like an interactive singing teacher.

The ideal workflow is:

`Paste YouTube URL`

→ `Analyze song`

→ `Create karaoke project`

→ `Practice song`

The user should need as little technical knowledge as possible.

---

# CRITICAL LEGAL / PLATFORM REQUIREMENT

Do not build the system around unauthorized downloading or circumvention of YouTube protections.

Verify current YouTube API/Terms requirements before implementing the ingestion layer.

Prefer:

* official YouTube APIs for metadata,
* embedded YouTube playback where appropriate,
* licensed/authorized audio sources,
* audio uploaded directly by the user,
* media for which the user owns or has permission to process.

If arbitrary extraction of audio from a pasted YouTube URL is not allowed by the relevant platform terms or deployment environment, do NOT secretly circumvent those restrictions.

Instead:

1. accept the YouTube link for song identification and playback reference,
2. ask the user to provide an authorized audio file when processing requires direct audio access,
3. keep the audio-source layer modular so properly licensed providers can later be added.

Design this as:

`AudioSourceProvider`

with implementations such as:

`UserUploadAudioProvider`

`LicensedAudioProvider`

and, only when permitted:

`AuthorizedRemoteAudioProvider`.

The rest of the product must work regardless of which authorized audio source is used.

# VOCAL SEPARATION

Where legally permitted and technically appropriate, separate the source into at least:

1. vocals,
2. accompaniment/instrumental.

Evaluate modern source-separation approaches before choosing an implementation.

Possible technologies include current maintained versions of:

* Demucs,
* MDX-based models,
* Open-Unmix,
* or another high-quality source-separation model.

Do NOT select a model solely because it is listed in this prompt.

Compare current quality, licensing, hardware requirements, inference speed, and maintenance status.

The separation system should ideally output:

`vocals.wav`

and

`instrumental.wav`

Optionally support additional stems later:

* drums,
* bass,
* other.

Cache processed results so identical authorized audio does not need to be processed repeatedly.

# LYRICS TRANSCRIPTION

Automatically determine the sung words.

Use a high-quality speech/singing transcription system.

Investigate current maintained models/services.

Potential options may include:

* Whisper-family models,
* WhisperX,
* commercial speech-to-text APIs,
* music/singing-specific transcription systems.

The goal is not only sentence transcription.

We need:

**word-level timestamps.**

Each word should eventually have approximately:

```json
{
  "word": "example",
  "start": 42.31,
  "end": 42.72,
  "confidence": 0.94
}
```

Store confidence.

Do not silently pretend uncertain transcription is correct.

# LYRICS ACCURACY

Singing transcription is difficult.

Design a multi-stage approach.

Possible approach:

1. isolate vocals,
2. transcribe isolated vocals,
3. obtain word-level timestamps,
4. segment into lyric lines,
5. calculate confidence,
6. let the user correct incorrect words.

Provide a built-in:

**Edit Lyrics**

mode.

The user should be able to change text without destroying synchronization.

If reliable licensed lyrics are available through an authorized lyrics provider, architect a `LyricsProvider` interface to optionally use them.

Never scrape copyrighted lyric sites in violation of their terms.

# MELODY / PITCH EXTRACTION

This is a core feature.

Analyze the isolated lead vocal and estimate the fundamental frequency over time.

Store approximately:

```text
timestamp
frequency_Hz
MIDI_note
confidence
```

Investigate current pitch-estimation technologies such as:

* CREPE,
* torchcrepe,
* pYIN,
* Basic Pitch,
* RMVPE,
* or another suitable maintained pitch detector.

Evaluate them specifically for **singing vocals**, not ordinary speech.

Ignore or mark:

* silence,
* unvoiced consonants,
* unreliable estimates,
* extremely low-confidence frames.

Smooth obvious pitch-tracking errors without destroying genuine vibrato.

---

# NOTE REPRESENTATION

Convert detected frequencies into musical-note representation.

For example:

`A4 = 440 Hz`

and MIDI/semitone representation.

Use:

`midi = 69 + 12 * log2(frequency / 440)`

where appropriate.

Store continuous pitch deviation rather than forcing every sample immediately onto a perfect note.

This allows the visualization to preserve:

* vibrato,
* slides,
* transitions.

---

# MELODY SIMPLIFICATION

Raw pitch extraction will contain thousands of samples.

Create two representations.

### Raw pitch

Used for detailed analysis.

### Simplified melody

Convert the raw contour into understandable singing targets.

Example:

`G4 → A4 → C5 → B4`

Determine note:

* start,
* end,
* target pitch,
* confidence.

Be careful with:

* vibrato,
* slides,
* ornamentation,
* rap,
* spoken passages,
* harmonies.

Do not generate fake notes when pitch confidence is poor.
